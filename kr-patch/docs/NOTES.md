# HWANSE.EXE 텍스트 구조 — 조사 노트

목표: 기존 정식 KR 번역(HWANSE.EXE에 내장)의 오타·오역을 찾아 제자리 수정. 새 번역 작업이 아님.

## 확정된 사실

- **텍스트 위치**: `GENSE.FLD`(필드/맵 데이터, ~2.85MB)가 아니라 **`HWANSE.EXE`의 PE `.data` 섹션**
  (raw offset `0x03A000`~`0x157E00`, size `0x11DE00`)에 있다. 흔한 한국어 단어(단서/사람/에게 등)
  빈도 스캔으로 확인 — `GENSE.FLD`에는 앵커 히트가 사실상 0이고 `.data`에만 1790개 몰려 있음.
  JP측(`GENSE.EXE`/`GENSE.FLD`)도 동일 구조(텍스트는 EXE, FLD엔 없음) — Shift-JIS 앵커 스캔으로
  대조 확인.
- **인코딩**: CP949(완성형 한글) 인라인 리터럴. 조합형 아님.
- **라인 종결자**: 리터럴 `'@'` (0x40) 바이트. NUL이 아니다. 전각 공백(`　` U+3000)과 전각
  구두점(`？！「」…`)을 문장 안에 그대로 사용.
- **포인터 없음**: 표본 문자열 여러 개의 파일 오프셋 · RVA · 절대 VA(`imageBase 0x400000 +
  RVA`)를 32비트 리틀엔디안 즉치값으로 파일 전체에서 검색 — 전부 0건. 즉 코드가 이 문자열들을
  주소 테이블로 참조하지 않는다. 스크립트 엔진이 이 영역을 순차 스트림으로 소비하는 것으로 보임
  (PC-98판과 같은 계열이지만 압축은 없음 — 사전 단어가 바이트 그대로 일치하는 것 자체가
  비압축의 증거).
- **추출 결과**: KR 14,689개 라인(`.data`의 약 2.4% — 884바이트 점프테이블 제외 후 최종
  수치, 아래 참조), JP(`GENSE.EXE`) 14,814개 라인. 추출→재조립 라운드트립 바이트 완전 동일
  확인(`kr-patch/tools/hwanse-text.js` 자체 테스트).
- **Shift-JIS 트레일 바이트 함정**: CP949는 2바이트 문자의 트레일 바이트가 `0x41`~`0xFE`라
  `'@'`(0x40)와 절대 겹치지 않지만, Shift-JIS는 트레일 바이트가 `0x40`~`0x7E`/`0x80`~`0xFC`라
  **한자/가나 2바이트 문자의 두 번째 바이트가 `0x40`일 수 있다.** 바이트 단위로 `'@'`를 재검색해
  라인을 나누면 이 경우 문자 중간이 잘려 라인 수가 거의 2배(25,841개)로 뻥튀기되는 버그가 있었음
  — 문자 경계를 지키는 단일 패스 워크로 수정(`extract()`가 트레일 바이트를 건드리지 않고 매 문자
  단위로 전진).
- **KR·JP 라인 순서는 서로 대응하지 않는다**: 반복 등장하는 화자 이름 태그로 확인 — "스마슈"(KR)와
  "スマッシュ"(JP)는 둘 다 정확히 579회 등장하고 "아타호"/"アターホー"는 863 vs 865회로 거의
  일치한다(내용 대응은 확실히 존재). 하지만 같은 이름의 각 등장 인덱스를 비교하면 KR이 JP보다
  체계적으로 앞서 있고 그 격차가 일정하지 않다(예: 1번째 등장 idx 76 vs 146, 2번째 88 vs 191) —
  즉 전역 순서가 다르다. 로케일 빌드마다 소스 파일 링크 순서가 달랐을 것으로 추정. **자동 정렬은
  포기하고, 사람이 KR을 리뷰하다 필요할 때 JP를 이름/키워드로 검색해 대조하는 방식으로 결정**
  (`kr-patch/tools/search-jp.js`).

## 길이 변경은 안전하지 않다 — 정책 확정

처음에 "포인터가 없으니 길이 변경도 안전할 가능성" 이라고 적었던 건 근거가 약했다. 실제로
확인한 건 **이 문자열들의 시작 주소를 가리키는 참조가 없다**는 것뿐이고, 이는 다음 위험을
전혀 배제하지 못한다:

- **문자열 뒤의 다른 데이터를 가리키는 포인터**: `.text`를 스캔해 `.data` 영역(VA
  `0x43C000`~`0x59F4C0`) 아무 곳이나 가리키는 4바이트 절대주소 즉치값을 세어보니 **5,643건**
  나왔다(정렬 안 된 우연한 매치도 섞여 있겠지만, 실제 데이터 포인터도 다수 포함될 것). 문자열
  하나 길이를 바꾸면 그 뒤 모든 바이트가 밀리고, 이런 참조 중 어느 것이든 깨질 수 있다.
- **`.reloc` 섹션**(0x1A24A 바이트, 상당히 큼): 로드 시 절대주소를 재배치하는 테이블인데,
  대상 주소의 실제 내용이 밀리면 엉뚱한 데이터를 가리키게 된다.
- **PE 섹션 중간에 바이트를 끼워 넣는 것 자체가 링커의 영역**: `.data`의 `SizeOfRawData`를
  바꾸면 그 뒤 모든 섹션(`.idata`, `.rsrc`, `.reloc`)의 파일 오프셋을 재계산해야 한다.

**정책**: 길이 변경 수정은 하지 않는다. `hwanse-text.js`의 `build()`가 이미 강제하는 **원본과
동일한 바이트 길이만 허용**을 최종 정책으로 확정한다(가설이 아니라 확정). 글자 수를 바꿔야만
고칠 수 있는 오타/오역을 발견하면, 같은 바이트 길이 안에서 표현을 바꿀 수 있는지 먼저 시도하고
(예: 조사·어미 교체로 음절 수 유지), 정 안 되면 그 항목은 스킵하고 `notes`에 이유를 남긴다.
길이 변경을 다시 검토하려면 이 파이프라인의 범위를 넘는 별도의 본격 역공학(포인터 재배치,
PE 섹션 리사이즈 자동화)이 필요하다.

## `.data`에는 두 가지 텍스트 포맷이 있다 (세 번째 시도는 실패해서 폐기)

대사(`@` 종결)만으로는 텍스트를 다 잡지 못한다 — `.data` 전체의 CP949 한글 바이트 중
17%가 대사 추출 범위 밖에 있었다. 나머지는 **이름/라벨 텍스트**(item·기술·시스템 메시지·
UI 라벨을 전부 포함하는 하나의 포맷)로, 처음 두 번의 접근이 모두 실제 사례에서 깨져서
세 번째 설계로 정착했다.

**1차 시도(폐기) — "전각 공백 패딩 앵커"**: CP949 이름 뒤에 전각 공백(리터럴 바이트
`0xA1 0xA1` = U+3000)이 슬롯의 남은 자리를 채운다고 보고, 공백 런의 시작점을 앵커 삼아
거기서부터 역방향으로 이름을 스캔. 역방향 확장을 한글 음절에만 한정해 노이즈는 잡았지만
(414개 추출, 겹침 0, 라운드트립 통과), **두 가지 실제 반례로 완전히 깨졌다**:
- 전각 공백이 항상 "트레일링 패딩"이 아니다 — **"지옥　다리후리기"**(Hell Leg Sweep)처럼
  화면에 진짜 보이는 띄어쓰기로 쓰이는 경우가 있다. 앵커 방식은 이걸 "지옥"과 "다리후리기"
  두 개의 별도 항목으로 쪼갰다.
- **패딩이 아예 없는 이름은 앵커를 찾을 수 없어 통째로 누락됐다** — "다리후리기" 자체가
  대표 사례(이름 끝나자마자 바로 스탯 바이트 시작).
결과적으로 같은 텍스트("도복", "갑옷", "지옥", "베기" 등)가 서로 다른 slot 폭으로 중복
추출되는 등 앞뒤가 안 맞는 항목이 나왔고, 이게 이 정책을 폐기한 직접적 계기다.

**2차 시도(채택) — "유효 문자 최대 연속 구간"**: 레코드 구조를 실제로 들여다보니 이름 뒤에는
항상 **텍스트가 아닌 제어 바이트**가 온다(레벨 1~4를 나타내는 작은 정수, 또는 단일 레벨
기술의 경우 `0xFF` 센티널). 둘 다 애초에 유효한 ASCII/CP949 선행 바이트가 아니므로,
"패딩이 어디서 시작하는지" 앵커를 찾을 필요 없이 **한글/ASCII/전각공백(`0xA1A1`)/가운뎃점
(`0xA1A4`, 일부 필살기명이 "비기·기술명" 형태로 이 문자를 씀)으로 이뤄진 최대 연속 구간을
순방향 단일 패스로 잡으면 저절로 올바른 경계**가 나온다(끝나는 지점이 자연스럽게 레벨
바이트나 `0xFF` 앞에서 멈춤). 이 방식은 대사(`hwanse-text.js`)와 똑같은 원리이고, 실제로
NUL 종결 시스템 메시지("환세취호전 ver.1.0", "드라이브　준비가　안됐습니다" 등)까지
같은 스캔으로 저절로 다 잡혀서, 원래 따로 두려던 "시스템 문자열" 포맷이 통째로 불필요해졌다
(그래서 `hwanse-strings.js`/`gense-strings.js`는 삭제).
- 노이즈 필터: 한글 2개 이상 요구 + 라틴 문자가 섞이면 3글자 이상 통짜로만 허용(짧거나
  동일 문자 반복 — `xxxddd`, `쟡hD덬` 스타일 — 은 전부 인접 스탯 바이트의 우연한 매치였음).
  ASCII 허용을 `charLenAt()` 자체에서 좁혀서(공백/마침표/숫자/글자만) 해결 — 이전에는
  `!` 같은 문장부호가 런에 끼어든 뒤 노이즈 필터가 "이름+문장부호" 전체를 통째로 버리는
  이차 버그가 있었음(예: "불타는　마검　　!" → 노이즈 판정 → "불타는 마검"까지 같이 유실).
  런에 안 들어오게 원천 차단하는 게 정답이었다.
- 2개의 ~2KB 구간(`0xca300-0xcaaf6`, `0xcab08-0xcb308`)은 명시적으로 제외 — 16비트 단조
  증가 값이 나열된 이진 룩업테이블(회전/스케일 애니메이션용으로 추정)인데, 값이 우연히
  CP949 한글 범위에 자주 걸려 노이즈를 만들었음.
- 최종: KR 389개(대소문자 섞임/3+ 반복 문자 필터 추가 후), JP(`GENSE.EXE`, 같은 방식으로
  재작성) 424개, 겹침 0, 결합 라운드트립 바이트 완전 동일.
- 라벨 노이즈 필터를 "발견 즉시 항목 전체 폐기"에서 **"노이즈 시작 지점에서 잘라 앞부분은
  살리기"**로 재설계(`findNoiseStart()`가 위치를 반환, 호출자가 거기서 truncate). 원래
  방식은 "대폭발　　　　　xxxddd"(스탯 바이트가 우연히 영문자로 보이는 꼬리) 같은 경우
  노이즈만 버려야 하는데 "대폭발"까지 같이 날렸음. 추가로 대소문자 섞임(`sZnPdd`)과 3회+
  동일 문자 반복(`xxxddd` = `xxx`+`ddd`)도 노이즈 신호로 인식하도록 필터 강화.

## 대사(`hwanse-text.js`)에도 이진 데이터 오염이 있었다

`0x3e538-0x3e8ac`(884바이트)는 `[2바이트 오프셋][0x40 또는 0x41][0x00]`이 반복되는 점프/
주소 테이블이다. 이 2바이트가 우연히 유효한 한글 음절로 디코드되는 경우가 많고, 레코드
자체의 `0x40`이 대사 종결자 `'@'`와 구분이 안 돼서, **한글 음절 1개짜리 가짜 "대사" 38개가
새고 있었다**(예: "욪", "턆", "휗"...). 구분법: 진짜 대사는 `'@'` 뒤에 문서화된 제어 코드
(`0x02`/`0x06`/`0x0A`/`0x10`)가 오는데, 이 노이즈 테이블 항목들은 예외 없이 `0x00`이 왔다
— 다만 이 신호를 전역 필터로 일반화하는 대신(위험도 높음), 이 특정 884바이트 구간만
`hwanse-text.js`에 하드코딩으로 제외했다(`hwanse-names.js`의 이진 룩업테이블 제외와 같은
패턴). 한글 음절 1개짜리 항목이 전부 노이즈는 아니었다는 점도 확인됨 — "일/월/화/수/목/금/
토"(요일)처럼 진짜 1음절 텍스트도 있었고(JP 쪽 `日月火水木金土`와 대응), 이런 것들은 전부
`'@'` 뒤에 진짜 제어 코드가 붙어 있어 위 구분법으로 제대로 살아남았다. "론"이 33회나
반복되는 것도 발견했는데(전부 진짜 제어 코드 뒤따름), 의미는 불명이지만 노이즈로 볼 근거가
없어 그대로 유지.

## 미확정 사항

라인 앞의 바이트(대개 `0x00`)와 `'@'` 뒤의 바이트(`0x02`/`0x06`/`0x0A` 등), 레이블 레코드의
레벨/스탯 필드(`01~04` 레벨 카운터, `0xFF` 단일레벨 센티널, 그 뒤 스탯 바이트)는 제어
코드/게임 데이터로 추정되나 의미까지 역공학하지는 않았다. 위 정책상 오타 수정은 텍스트
슬롯 내부만 건드리므로 이걸 건드릴 필요가 없어 스코프 밖으로 남겨둔다.

## 산출물

- `kr-patch/tools/hwanse-text.js` — KR 대사 `extract(buf)` / `build(buf, entries)`.
- `kr-patch/tools/hwanse-names.js` — KR 이름/라벨(기술명·아이템명·시스템 메시지·UI 라벨
  전부 포함) `extract(buf, excludeMask)` / `build(buf, entries)`. "유효 문자 최대 연속
  구간" 방식(위 참조).
- `kr-patch/tools/gense-text.js` / `gense-names.js` — JP 대사·라벨 `extract(buf)` (읽기
  전용 참고용, build 없음).
- `kr-patch/tools/search-jp.js` — JP 참고 덤프(대사+라벨)를 키워드로 검색. 정렬이 안
  되므로 오타 리뷰 중 필요할 때 이걸로 대조.
- `kr-patch/tools/editor.js` + `editor.html` — 로컬 웹 에디터(`node kr-patch/tools/editor.js`
  → `localhost:8182`). 대사/이름·라벨 탭, 검색, 행별 수정+저장. 서버가 바이트 길이를
  재검증하고, `labels`는 짧아진 교정문을 전각공백으로 자동 패딩(`dialogue`는 정확히 일치
  해야 함 — 패딩 개념 없음). JP 대조는 순서가 안 맞는 게 검증돼 있어 비례 위치 추정 기능은
